# Test data and authentication map

## Isolation

Every test owns its data:

- users are generated by `uniqueUser()`;
- events are generated by `uniqueEvent()`;
- bookings are generated by `bookingInput()`;
- no test depends on a pre-existing event, user, booking, or execution order.

Use API setup unless the UI setup itself is under test. Do not add shared accounts or hardcoded IDs to make a test faster.

## Cleanup

`ownedEvent` removes bookings associated with the owned event and then deletes the event after a successful test. Failed-test data is retained for diagnosis according to the fixture policy. Cleanup must stay scoped to resources created by the current test.

When a test using `ownedEvent` fails, its non-secret event ID and title are attached as `owned-event.json` so retained state can be identified without logging credentials or tokens.

When a test creates an additional resource outside a fixture, clean it in a `finally` block and preserve the original assertion failure.

## Authentication

- Registration creates a unique user and returns an authentication token.
- `authenticatedApi` applies the token to API clients.
- `authenticatedPage` performs UI login using the generated credentials.
- `getEventWithRecovery()` re-authenticates once only for an idempotent event read after HTTP 401.
- Mutating operations are never automatically replayed after expiry.
- Tokens, passwords, and storage state must not be logged or committed.

## Synchronization

Use Playwright auto-waiting, response predicates, URL assertions, and visible-state assertions. Never use `waitForTimeout`, `networkidle`, arbitrary polling, or hidden retries.
